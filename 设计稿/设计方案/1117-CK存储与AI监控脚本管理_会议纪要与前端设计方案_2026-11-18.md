## 一、会议纪要

### 议题 1：CK（ClickHouse）数据接入与查询口径

**现状（后端说明）**
- 186 上已建两个 CK 库（高版本、低版本各一），133 的贝壳等数据已同步到 CK，数据在持续增量同步。
- 行情数据（在 133 建的）目前没有在 186 的 CK 表里，待确认。
- 前端「数据查询」已能查 CK 表；MySQL 侧同名表只有约 1000 条样例，最新数据只在 CK。
- 广发早期导入的老数据（2023 年左右）没有 `source_id`，所以按源关联查不到，这部分不属于缺陷。

**技术负责人提出的问题**
1. 用户在界面上看不出一张表在 CK 还是 MySQL，不知道该查哪个库。
2. 「存储类型 / 读写类型 / 引擎」这些选项放在数据中心里，用户一般不会去那里改，入口放错了。
3. 查数据应该以「源」为入口：在源上选表查询，按表配置的库类型自动查对应的库。
4. 一张表先进 MySQL、后来同步到 CK，切换查询库的路径要清楚，同步任务要能看到记录。

**结论**
- **新建表时提供存储类型选项（CK / MySQL）**，数据中心「新建表」和源上「表配置 → 新建表」两处都要有，两处字段和行为保持一致。
- 选 CK 时**读写类型默认「读写」**、引擎默认 `ReplacingMergeTree`（带版本去重）；读写类型、引擎、排序列、分区放进「高级」并默认收起，普通用户只选库类型。
- **在源、表上明确标识库类型**（CK / MySQL），用户一眼能看出一张表查哪个库。
- MySQL → CK 的切换走数据中心现有的「同步到 CK」，同步记录要能查到。

### 议题 2：新平台切换上线方案（186 并行验证 → 生产）

**分歧**：发言人4 认为新平台底层数据结构、流程结构都改了，老平台（2806/2807 后端）直接切过去会有部分功能不兼容，没法回滚；技术负责人不接受直接替换生产的风险。

**结论（定稿）**
1. 在 **186 测试环境**上重新部署一套处理机，接正式调度。
2. 由「钢铁/安达」（人名待确认）把现有**广发源（约 100 多个网站）全部迁到 186 跑起来**。复杂的多流程源必须跑通，单流程源要求可以放宽；需要登录的采集程序由对应人员补配置。
3. 测试同事同步核对每个源的数据，顺带熟悉数据。
4. 每个源**连续跑约两周没问题**后，把 186 的整套配置拷到生产（80/2806 对应库）再切换；回滚就退回原 34 DB。
5. 处理机尽量放在**外网机器直连 186**，不要绕内网：内网上行带宽（约 50M）已接近上限（发言人4 多次实测）。
6. 申万、中金目前不在这套环境上，数据在库里，先以广发为主。

> 本议题不涉及前端改动；前端发布到 186 时照常执行，构建参数按 AGENTS.md 中 186 的约定。

### 议题 3：AI 监控脚本改走统一的「代码生成 → Git → 部署」体系（重点）

**背景**：开发人员已把原本嵌在流程节点里的 AI 监控脚本（原「综合/zhonghe」的实现）拆出来，在监控中心可以独立新增并跑通；脚本目前以实体文件形式放在 186 上（MinIO/OSS 路径），生成时调的是原服务的 AI 接口。技术负责人认为这套做法跟他做的「网页抓取代码生成」设计重复，存储和部署方式也不对，要求统一。

**统一后的链路（技术负责人设计）**

```
监控中心 新建监控
  └─ 读取「节点提示词模板（数据监控）」：系统提示词 = 框架/规范；用户提示词 = 业务描述（按选项动态拼接）
      └─ 点「生成脚本」→ 选智能体（可全选空闲资源池）→ 调智能体代码生成接口
          └─ 生成的 .py 自动提交到 Git 代码仓库 monitor 目录
              └─ 部署配置：机器从 Git 拉代码到运行目录，主程序（框架）常驻
                  └─ 统一调度平台按执行计划下发任务（MQ）→ 主程序按任务里的脚本标识调用对应 .py → 回写结果
```

**会上定下的要点**
| 项 | 结论 |
|---|---|
| 归属 | 后端由**后端开发工程师**负责（技术负责人当场定性：「这是你的活」），开发人员配合前端 |
| 第一步 | 后端先摸清原逻辑：脚本如何生成、存在哪、怎么执行、调的哪个 AI 接口（会上有人说是经 CC Switch 中转的代理，待核实） |
| 提示词 | 拆成**系统提示词 + 用户提示词**两段，配进「系统设置 → 节点提示词模板」的数据监控类型；新建监控时自动读取并填充变量 |
| 存储 | 脚本不再放 MinIO，**统一提交 Git**；系统设置 → 代码仓库已建「数据监控」类型目录 `monitor` |
| 目录结构 | `monitor/` 根放主程序（框架）；`monitor/<sourceId>/<监控标识>.py`，一个源下可有多个监控脚本 |
| 监控标识 | 用监控 ID 或规则 code 命名；code 需保证全局唯一，否则用监控 ID（后端倾向 ID，待与黄总确认） |
| 执行 | 主程序是「模板方法」：头尾（取任务、保存数据、回写结果）统一，中间调用生成的监控函数；生成脚本里**不写 MQ 消费、不写保存逻辑**，提示词里约定入口函数签名和返回格式 |
| 调度 | 去掉监控自建的调度，**接入统一调度平台**：每个监控的执行计划（cron）进调度表，按任务方式下发；任务内容必须带脚本标识（sourceId + 监控 ID/code），调度和任务表结构问黄总 |
| 数据保存 | 监控结果写哪张表、什么格式，要写进系统提示词，让 AI 按固定格式输出 |
| 部署 | 复用「部署配置」：选机器、目标目录，选主程序作为启动入口；配置节点由技术负责人的后端生成 |
| 画布 | **数据监控不做成流程节点**，不在画布上拉节点；监控在源的监控页里独立管理 |
| 规则处理 | 同样按这套方案（两段提示词 → 智能体生成 → Git → 框架执行）设计 |
| 环境 | 先在 186/2807 跑通；217 还缺不少后端，前端开发人员与黄总沟通 |

**执行结果字段**：任务列表里的「执行结果」目前直接展示原始返回，要求解析成**状态（成功/失败）**和**错误消息**两列分开显示，不要把整段原文塞在一个字段里。

## 二、前端设计方案

### A. 新建表：存储类型选项（CK / MySQL）

**现状**
- 数据中心新建/编辑表抽屉 `views/DataView/EntryEditorDrawer.vue:357-389` 已有「数据源类型 / 读写类型 / 存储引擎 / 排序列 / 分区」，全部平铺展示。
- 源上表配置的新建表弹窗 `views/FlowCanvas/inspector/TableEditDialog.vue` **没有库类型字段**，从源上新建的表只会是默认 MySQL。

**改动**
1. **抽公共表单片段** `components/entry/EntryStorageFields.vue`（命名待定），两处共用，保证字段、默认值、校验一致：
   - 主区只保留「存储类型」：分段按钮 `MySQL | CK`，默认 MySQL；下方一行灰字说明「CK 适合大数据量查询分析，数据按版本去重」。
   - 「高级设置」折叠区（默认收起）：读写类型、存储引擎、排序列、分区字段。
   - 默认值沿用 `EntryEditorDrawer.vue:126-132` 现有口径：新建 `opType = wr`；CK 引擎 `ReplacingMergeTree`、排序列 `ENTRY_ID`；MySQL 引擎 `InnoDB`。
2. `TableEditDialog.vue` 接入该片段，提交时把 `dsKind / opType / storageEngine / sorted / partColumn` 带上；需确认源侧新建表接口是否接收这些字段（见第三节后端确认）。
3. 编辑已有表时：存储类型只读（已有物理表不能直接换库），旁边给「同步到 CK」入口（复用 `QuickCkSyncDialog.vue`）。

### D. 监控中心：AI 脚本生成改走智能体 + Git

**现状**
- 监控编辑器 `views/FlowCanvas/result/monitor-editor/`：`generation.ts:190 generateMonitorScript` 调 `/api/answer/data-process`（SSE）生成，正文/OSS 路径写进 `ck_source.check_conf`。
- 网页抓取已有完整的智能体生成弹窗 `views/FlowCanvas/inspector/SiteScriptGeneratorDialog.vue`：两段提示词、智能体选择（含全选资源池）、仓库/目录选择、生成后提交 Git。

**改动**
1. **复用而不是重写**：把 `SiteScriptGeneratorDialog` 里的「提示词双栏 + 智能体选择 + 仓库目录 + 提交 Git」抽成通用组件（如 `components/codegen/AgentScriptGenerator.vue`），按 `nodeType` 区分网页抓取和数据监控。
2. **新建/编辑监控弹窗**（`CheckEditDialog.vue` / `MonitorConfigEditor.vue`）
   - 「业务描述」等现有选项保持不变，作为用户提示词的变量来源，联动生成用户提示词。
   - 打开时按 nodeType = 数据监控读取「节点提示词模板」的默认模板，填充系统提示词和用户提示词，两栏都可以手工修改。
   - 「生成脚本」改为打开通用生成组件：默认仓库 = 代码仓库中数据监控类型的目录（`monitor`），目标路径预览 `monitor/<sourceId>/<监控标识>.py`，只读展示。
   - 生成完成后展示文件路径、提交状态（已推送 / 仅本地提交），保存监控时把 `repoId / directoryId / scriptPath / commit` 写入监控配置，**不再保存脚本正文和 OSS 路径**（旧数据只读兼容展示）。
   - 新建监控还没有 ID 时，先保存草稿拿到 ID 再生成（或按后端约定用 code），避免文件名缺标识。
3. **执行计划**：保留现有 `CronBuilder.vue`，保存时 cron 交给统一调度（字段名以后端为准）；界面上去掉「自建调度」相关的状态展示。
4. **不加画布节点**：节点类型列表、画布节点面板里不出现「数据监控」节点；已有的监控节点只读兼容。
5. 系统设置 → 代码仓库：确认数据监控类型目录在「全部节点类型」筛选下可见（会上演示时新建的 monitor 目录刷新后一度不显示，需复现修复）。

### E. 执行结果拆分（2026-11-18 已实现）

> 更正：会上说的「执行结果」列是 **任务列表**（`views/FlowCanvas/result/TaskView.vue`，4c078546 新增，直接展示 `taskResult` 原文），不是监控列表。

- 表格态把「执行结果」拆成两列，紧跟任务「状态」：**结果状态**（成功 / 失败 / 执行中 / —，小标签）＋ **错误消息**（两行省略，点击打开详情）。卡片态（任务中心）显示「状态标签 + 错误消息」，空结果仍按任务状态提示。
- **186 实测契约**（2026-11-18，E/C/L 各抽样 1000+ 条）：执行端统一回写 `{"IsSuccess":"true"|"false","StrTaskId":"…","ErrorMessage":"…"}`，少量带 `Params` 的变体里 `IsSuccess` 是布尔。成功任务 `ErrorMessage` 用 `-` 占位；**失败任务的 `ErrorMessage` 全部是空串**；运行中任务 `taskResult` 为空。
- 解析在 `utils/flow/taskResult.ts`：键名不区分大小写，优先 `IsSuccess` + `ErrorMessage`（`-` 视为空）；兼容 `status/success/code` 和 `error/message/msg` 等写法；JSON 数组取第一条；判不出显示「—」，不猜成功。实测 900 条中，解析结果与任务 state 完全对应（E→失败、C→成功、L→执行中）。
- 原文保留在悬停提示和详情抽屉里。任务本身的「状态」列仍以接口 state 为准，不受结果内容影响。
- **后端待办**：失败任务的 `ErrorMessage` 目前没有填写，错误消息列在失败行只能显示「—」；需要执行端把失败原因写进 `ErrorMessage`。
