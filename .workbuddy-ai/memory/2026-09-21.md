### 其中一条的根因已查清：`编辑系统提示词：保存后写回 systemPrompt`

结论：**不是测试选择器写错，是真实的产品级覆盖问题**。用探针（写文件，见下）拿到的时序：

```
[emit] onSystemPromptChange value= "新的系统提示词"
[patch] systemPrompt= "新的系统提示词" | id= rule-1 | isRule= true | nodeIsRule= true
[emit] after-patch orchCfg.systemPrompt= "新的系统提示词"      ← 保存成功，store 已写入
[watch] applied= "源表=JD-商品基础…" | seq= 6 6 | cur= "新的系统提示词"
[patch] systemPrompt= "源表=JD-商品基础…"                     ← 被自动拼接结果覆盖回去
```

机制：`RuleOrchestrationTab.vue` 里那个「按表/字段自动拼接系统提示词并写回」的 watcher
（`watch` 依赖 `inputFieldOptions` / `outputFieldOptions` / `sourceTableName` / `promptCategory` 等，
末尾 `if (applied !== orchCfg.value.systemPrompt) patch({ systemPrompt: applied })`）
在工作台保存之后**又跑了一轮**，把用户手改的提示词覆盖成刚渲染出来的模板。
它的 seq 守卫（`refreshSeq !== promptRefreshSeq`）只防「旧请求晚到」，不防「用户已手改」。

即：**只要表/字段相关的异步数据（字段选项、表名）在工作台保存之后才落地，
用户刚保存的系统提示词就会被静默覆盖**。字段选项是异步加载的，所以这是个真实的竞态窗口，
不只是测试环境问题。现实路径还有更宽的一条：用户改完提示词保存，之后去「表配置」改一个字段，
回来提示词已被换回模板。

#### 已修（0921 同日）

口径不靠新发明——项目里已有既定做法：`describeTouched`（数据监控描述回填）、
`translateLangsTouched`（翻译语言回填），都是「用户改过后不再被自动回填覆盖」
（0921 翻译助手设计方案 §2.1 有明文）。照抄同一套：

| 文件 | 改动 |
| --- | --- |
| `RuleWorkbenchDialog.vue` | `defineEmits` 加 `'prompt-saved': []`；`savePrompt()` 里**先** `emit('prompt-saved')` 再 emit 那几个 update（顺序要紧：先置位再回写） |
| `RuleOrchestrationTab.vue` | 新增 `promptTouched`（声明放在 `describeTouched` 旁，**必须在 `watch(id,…,{immediate:true})` 之前**，否则 TDZ）；`onPromptSaved()` 置位；`watch(id)` 里复位；自动拼接 watcher 的回写处加 `if (promptTouched.value) return`；模板加 `@prompt-saved="onPromptSaved"` |

关键设计取舍：
- 只挡「回写」，**不挡「取模板」**——`articlePromptMissing` / `tagPromptMissing` 仍照常更新，
  界面还能提示模板缺失。
- 手改后即使改表/字段也不再把提示词换回模板（会留着手写内容 + 过期的占位符）。
  这是 `touched` 惯用法固有的取舍：静默丢用户输入比留一个陈旧占位符更糟。
- `loadPromptTemplate` 的自动 emit 不走 `savePrompt()`，所以自动回写不会被误判成用户编辑。

同一套旗标也补在了 `onApplySwitch`（切换已有配置）里：`if (detail.systemPrompt) promptTouched.value = true`。
加条件而不是无条件置位——`detail` 没带提示词时 `patch` 用的是当前值，没有覆盖风险，
不该顺手挡掉后续正常的重拼。这条路径对**数据监控 / 数据校验 / 文章打标签**节点是真会触发的
（它们的自动拼接 watcher 是活的），对 web-list 这类抓取配置节点不会（watcher 提前 return）。

验证：`14 failed | 101 passed` → **`13 failed | 102 passed`**，新增失败为空，
修好的正好是 `编辑系统提示词：保存后写回 systemPrompt，取消不写回` 这一条；
三条「自动拼接」用例（进入编排配置自动拼接 / 表配置字段变化后规则处理重拼 / 数据监控重拼）仍绿。
该用例尾部又补了一步「保存后再改 inputFields」，把「手改值扛住重拼」变成显式断言（原来只靠异步竞态偶然触发）。

### 调试技巧：这个环境里 `console.log` 的行会被 reporter 吃掉

用 `npx vitest run ... 2>&1 | grep '^\[probe\]'` 抓探针时，**同一用例里 3 条 log 只出来 1 条**
（行被 reporter 的 ANSI 重绘吞掉），会得出错误结论。可靠做法：
组件和测试都往 `globalThis.__probe` 数组 push，测试末尾 `writeFileSync('/tmp/probe.log', ...)` 落盘，
再 `cat` 文件——不受 reporter 影响。本次就是靠这个才定位到覆盖时序。
