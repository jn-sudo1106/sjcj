# 数据监控节点类型持久化 —— 后端改动说明

> 面向后端同学。背景：前端（front-ce）新增「数据监控」节点，复用「规则处理」的配置，
> 但步骤（Step）结构里缺少能区分两者的类型字段，前端只能靠节点名正则识别，改名即失效。
> 本文约定后端需要落地的字段改动，以及前端就绪后的配套动作。

## 一、问题

- 前端新增节点模板「数据监控」（内部模板码 `monitor`），配置上与「规则处理」（`rule`）**复用同一套**规则种子。
- 区分两者的唯一结构信号是前端内存里的 `NodeConfig.template`（`'monitor'` vs `'rule'`），但**这个字段当前不落库**。
- 步骤回读接口 `item/next/nextConfigPaged` 返回的 Step 里，能用来判断节点类型的只有 `type`（旧步骤类型）和 `name`：
  - `type` 值域是旧平台步骤类型（`entry`/`list`/`detail`/`login`/`rule`/`clean`/…），没有 `monitor` 这一项；
  - 新建「数据监控」步骤时，`type` 会继承前置步骤或被写成默认值 `entry`，无法和「规则处理」区分。
- 因此前端目前**回退到按节点名是否含「数据监控」四字来补类型**（`flowModel.seeds.ts` 的 `templateKeyForStep` / `buildNodeForStep`），
  用户一旦把节点改名成不含这四个字的名称，重新加载流程后节点会退化成「规则处理」。

## 二、诉求（推荐方案）

**在步骤 Step 结构新增一个字段 `nodeTemplate`（string，可空），用于承载新平台的节点模板码，前后端原样存取。**

选新字段、不动 `type` 的理由：
- `type` 是旧平台步骤类型，其值决定旧执行器/旧逻辑的走向，混入 `monitor` 这类新平台模板码会影响旧平台行为，风险不可控。
- `flowCode` 实测恒为 `WEB_SNATCH`，语义是旧「步骤模板编码」，同样不宜复用。
- 新增独立字段语义最清晰、对存量数据零影响。

### 字段约定

| 项 | 约定 |
|---|---|
| 字段名 | `nodeTemplate`（建议；若后端更倾向 `template` 也可，但需避开已有的流程模板 `templateId` 语义） |
| 类型 | `string`，可空；历史步骤无此字段 |
| 取值 | 新平台节点模板码，见下表 |
| 写入 | 步骤写入 payload（见下） |
| 回读 | `nextConfigPaged` 响应原样返回 |

### 节点模板码枚举（前端 `NodeConfig.template` 值域）

| 分组 | 模板码 |
|---|---|
| 规则类 | `rule`（规则处理）、`monitor`（数据监控，本次新增） |
| 采集类 | `web` `app` `file` `python` `browser-html` `wechat-html` `login` |
| 数据处理 | `process`（历史 `parse` `ocr` `ai` `map` `clean` `dedupe` `check` 仍可能出现在存量节点） |
| 逻辑 | `decision` `parallel` |
| 引用类 | `metric` |
| 通知类 | `mail` `alert` |
| 其他 | `custom` |

> 后端只需**原样透传**这个字段（存了再回读返回即可），无需理解其语义，也不必校验值域。

## 三、涉及接口

### 写入（两个接口的 payload 都需带 `nodeTemplate`）

| 接口 | 用途 | 传参方式 | 位置 |
|---|---|---|---|
| `POST /v1/item/next/saveItemConfig` | 新建子步骤 | POST + query string（`params`，非 JSON body） | `legacyAdapters.ts` `stepToSaveItemConfigPayload` |
| `POST /v1/item/next/stepModify` | 修改子步骤 | POST + JSON body | `legacyAdapters.ts` `stepToStepModifyPayload` |

- 两个接口共用字段构建函数 `stepWritePayloadBase()`（`legacyAdapters.ts:1119`）。
- 前端就绪后会在此函数里加一行：`nodeTemplate: step.nodeTemplate ?? undefined`（注意 saveItemConfig 走 query string，字段需后端在 query 参数里接收）。

### 回读

| 接口 | 用途 |
|---|---|
| `GET /v1/item/next/nextConfigPaged` | 子步骤分页 / 流程图读取 |

- 响应里每个步骤原样返回 `nodeTemplate`（历史步骤无此字段，返回 null 或不返回均可）。

## 四、兼容性要求

- **历史步骤无 `nodeTemplate`** → 前端回退到现有 `type` 别名映射 + 节点名正则推断，行为与现在完全一致，存量流程不受影响。
- **新建/保存的步骤带上 `nodeTemplate`** → 前端优先读它做节点模板路由，不再依赖节点名，改名不再丢类型。
- 后端新增字段后，**不要**为此改动 `type` / `flowCode` 的现有取值与默认值逻辑。

## 五、前端配套改动（后端字段就绪后，前端侧自行完成，仅告知）

1. `api/types/source.ts`：`Step` 接口加 `nodeTemplate?: string`。
2. `utils/flow/stepPersist.ts` `mergeStepForWrite()`：写入 `nodeTemplate: cfg.template`。
3. `api/legacyAdapters.ts` `stepWritePayloadBase()`：payload 加 `nodeTemplate`。
4. `views/FlowCanvas/canvas/flowModel.seeds.ts`：
   - `templateKeyForStep()` 优先读 `step.nodeTemplate` 命中直接返回；
   - `buildNodeForStep()` 移除/降级「按节点名含『数据监控』补 template」的正则兜底（保留为无 nodeTemplate 时的兼容兜底）。

## 六、验收口径

后端联调通过标准（前端配合验证）：

1. 新建一个「数据监控」节点并保存 → `saveItemConfig` / `stepModify` 请求里出现 `nodeTemplate='monitor'`。
2. 重新加载该流程 → `nextConfigPaged` 返回的对应步骤带 `nodeTemplate='monitor'`，前端画布正确显示为「数据监控」节点。
3. 把该节点改名成不含「数据监控」的任意名称再保存、重新加载 → 仍是「数据监控」节点（不再退化成「规则处理」）。
4. 存量流程（无 `nodeTemplate`）加载行为与改动前一致。
